## 1. 框架选择

主框架取**带崩溃切点的离散状态机**。系统的并发空间已被单一文件锁压成一维，真正决定正确性的是状态转移的原子粒度与崩溃点位置，而非交错顺序。辅助框架两项：**关系代数**用于路径到 ID 的映射性质，**序列投影**用于 prune 对提交流的过滤与重放。

不用概率模型：唯一随机量是 ID 前缀碰撞，其量级可忽略，且实际故障是确定性的（见 §3.2）。不用范畴或度量结构：本问题没有比「保存」更强的高层抽象，硬套只会把可判定的小问题升格为宏大叙事。

[另一解] 若把 git 视为外部权威存储，系统等价于「两个存储之间无事务的复制」。结论不变，只是 `I_5` 的表述改为复制一致性。

## 2. 形式化陈述

### 2.1 状态与操作

设 $P$ 为规范化绝对路径集合，$X$ 为 ID 集合，$B$ 为字节串，$V \subseteq \mathbb{N}$ 为版本号。

状态 $S = (D, I, \mathcal{G})$：$D : P \rightharpoonup B$ 为磁盘内容；$I : P \rightharpoonup E$ 为索引，$E = (x, m, h)$；$\mathcal{G} = (c_0, \ldots, c_n)$ 为提交序列。

派生函数：$\mathrm{ver}(c)$ 由主题串解析；$\mathrm{path}(c)$ 为该提交触碰的路径；$\mathrm{blob}(c)$ 为该路径下的内容；$V(p) = \{\mathrm{ver}(c) : \mathrm{path}(c) = \mathsf{rel}(\mathsf{id}(p))\}$。

操作集合 $\{\mathrm{edit}, \mathrm{revert}, \mathrm{mv}, \mathrm{prune}, \mathrm{hook}\}$，每个操作分解为原子片段序列。崩溃模型：进程可在任一片段边界终止，事后状态为该前缀的合成，锁由内核在进程死亡时释放。

### 2.2 被检查的不变量

- $I_1$ **ID 单射**：$\mathsf{id} : \mathrm{dom}(I) \to X$ 为单射。
- $I_2$ **版本单调**：若 $c$ 追加于 $p$，则 $\mathrm{ver}(c) = \max V(p) + 1$，且版本号不复用。
- $I_3$ **基线语义**：$0 \in V(p) \Rightarrow \mathrm{blob}(c_0) = $ 纳管时刻的 $D(p)$。
- $I_4$ **先持久化后破坏**：$\mathrm{revert}$ 对 $D(p)$ 的可见改写发生前，存在满足 $\mathrm{blob}(c) = $ 目标内容的持久提交。
- $I_5$ **索引-仓库一致**：$\forall p \in \mathrm{dom}(I)$，$|V(p)| \ge 1$，且每个 $v \in V(p)$ 的 blob 仍在对象库中；反向亦然。
- $I_6$ **钩子序**：hook 在提交之后、解锁之前执行。
- $I_7$ **保留**：$|V(p)| \le \max(m_p, m_g)$，其中 $m = 0$ 表示不限制。
- $I_8$ **单写者**：所有写操作在锁 $\ell$ 下串行。
- $P$ **重放前提**（prune 定理的假设）：$\mathcal{G}$ 中每个提交都是 bakon 提交，且恰好触碰一个路径。

## 3. 交叉论证

### 3.1 崩溃一致性

$I_4$ 的实质是「破坏性写不得先于恢复路径的持久化」。在 edit 中，破坏由编辑器施加，恢复路径是用户自己的撤销，故 $I_4$ 只要求弱形式；在 revert 中，破坏由工具施加，恢复路径只有仓库，故 $I_4$ 必须严格成立。实现把两个操作写成同一条流水线（写回、提交、裁剪、钩子），把用户意图错当成了工具意图，于是 F3 出现：提交失败后目标已是旧版本内容，而 `B` 状态没有任何记录。

同一视角下 $I_3$ 的失败形式不同：它要求「索引记录」与「基线提交」原子。两个存储之间没有事务，实现选择了先写索引，于是崩溃或提交失败把 $I_3$ 降级为「若未失败则成立」（F6）。该不变量的最弱前提是「索引为可重建缓存」，而这恰是待裁决点之一。

### 3.2 函数与单射性

定义 $\mathsf{id}(p) = H_{48}(\mathrm{abs}(p))$，取 sha256 前 6 字节。$\mathsf{id}$ 是 $P$ 上的函数。`mv` 保留 $x$ 而更换键，纳管新路径时又重算 $\mathsf{id}$，两条规则合起来使「被腾空的路径再次纳管」必然落入同一像：$\mathsf{id}(p') = \mathsf{id}(p)$ 而 $p' \ne p$。F8 由此确定发生，与哈希强度无关；$2^{48}$ 空间在 $10^{4}$ 规模下的偶然碰撞概率约 $10^{-7}$，可以忽略，真正的缺陷是模式层面的：ID 同时承担「路径的函数」与「与路径解耦的稳定标识」两个互斥角色。

后果不止展示混乱：$\max V$ 在共享历史上计算，两条路径的版本号交错；`revert` 会把另一条路径的内容写进本文件。

### 3.3 序列投影与成本

prune 是 $\mathcal{G}$ 上的过滤 $G' = \{c \in \mathcal{G} : \mathrm{hash}(c) \notin \mathrm{dropped}\}$。$I_2$ 在投影下保持，因为版本号编码在主题串中而非位置中；$I_7$ 亦保持。

投影定理依赖前提 $P$，而 $P$ 是一个**全局**性质，机制只能保证**局部**性质：锁保证 bakon 自己写的提交满足「一提交一路径」，无法保证仓库中不存在其他提交。实现既不校验 $\mathcal{G}$ 的归属，也不校验每次提交的路径数，`ChangedBlob` 直接取第一条差异行。于是 $P$ 被静默违反时，重放不报错，而是产出错误的历史（F1）。

成本律同理：重放代价为 $O(|\mathcal{G}|)$（每提交 4 次 git 调用），与 $V(p)$ 无关。由于保留检查嵌入每次 edit，稳态 edit 成本由全库规模而非本文件规模决定，这与「单文件工具」的定位冲突（F12）。

### 3.4 张力与待确认

$I_5$ 依赖索引与 git 之间的一致性，而系统没有跨存储事务。若索引是**权威数据**，必须引入顺序不变量并把 `verify` 扩展为双向校验；若索引是**缓存**，$I_5$ 应放松为「最终可重建」，并允许在崩溃后重建。当前实现处于两者之间：写入顺序按权威数据处理，检查完备性按缓存处理。

$I_1$ 的修复需要改变 ID 的交换格式，旧条目无法回填盐值，属于兼容性决定。$I_4$ 的强形式要求 revert 拒绝覆盖分歧内容，或覆盖但记录。仓库归属的判定方式影响既有 store。三者均记为待裁决项。

## 4. 边界与反例

### 4.1 四个 P0 的展开

**F1 重写无关仓库。** 造一个含两文件的提交 $c$，令 store 指向该仓库根，触发 prune。重放后 HEAD 只剩 `a.txt`，`b.txt` 从历史消失，原提交被 gc 回收，工作树出现 `A b.txt`。根因是 §3.3 的 $P$ 未被校验：`ChangedBlob` 取首条差异行，外部多文件提交的其余路径在重建树中蒸发。前提：store 指向既有仓库根，且触发过一次 prune。

**F2 提交写进外层仓库。** store 位于某工作树子目录时，`git init` 被跳过，提交路径相对外层仓库根记录为 `repo/files/<id>`，而 bakon 读取的是 `files/<id>`。`log` 直接以 `fatal: 路径不在 <commit> 中` 失败，`prune` 以缺少 `.git` 失败，而 `edit` 仍报告成功。前提：store 复用既有工作树。

**F3 与 F4 写回语义。** 计数器实验：revert 时用 pre-commit 阻断提交，目标文件仍被改成旧版本内容，版本数不变，`B` 无记录。符号链接实验：revert 后链接变成 `-rw-rw-r--` 普通文件，真实目标保留编辑后的内容，两者从此分叉。inode 由 14551000 变为 14551043，硬链接与 inode 级元数据因此分离；ACL 与 SELinux 标签的丢失是该事实的推论。

**F5 静默丢弃分歧。** 纳管后手工改写文件，再 revert 到最新版本：输出 `already matches version 1`，文件被覆盖为仓库内容，版本数不变。该路径不触发钩子，也不产生任何记录，$I_4$ 的弱形式在此退化为零。

### 4.2 其余反例的输入形态

| 编号 | 输入 | 观测 |
|---|---|---|
| F6 | 基线提交被 pre-commit 阻断 | 索引留下条目；`log` 为空；`verify` 报 ok；重跑后编辑后内容成为 `ver 0` |
| F7 | 索引中加入不存在的 ID | `verify` 返回 `ok`，退出码 0 |
| F8 | 纳管 `b1`，`mv b1 b2`，重建 `b1` 并纳管 | `path` 显示同一 ID；`log b1` 与 `log b2` 相同，版本 $0..3$ 内容交替 |
| F9 | 全局上限 2，per-file 设为 0 | 版本数保持 2，未达「不限制」的 6 |
| F10 | 单版本文件执行 `diff` | 退出码 1，与「有差异」不可区分 |
| F11 | 钩子设为 `bakon prune` | edit 在 4 s 后仍未返回，超时终止 |
| F13 | `GIT_DIR` 指向另一仓库 | `log` 无输出、退出码 0 |
| 补 | `mv` 至尚未创建的新路径后 `revert 0` | 新路径被创建，旧路径保留，两处内容同时存在 |
| 补 | `max_versions = 1` | 基线 `ver 0` 在首次变更后被裁剪，`revert 0` 报 `has been pruned` |

## 5. 落地指导

| 修复 | 形式依据 | 代价与前提 |
|---|---|---|
| `Init` 判定改为「`rev-parse --show-toplevel` 等于 store 且 `.git` 存在」，并在初始化时写仓库标记文件 | F1、F2，$P$ 的守卫 | 既有 store 需一次确认或迁移 |
| 所有 git 调用显式指定 `--git-dir`/`--work-tree`，并在环境中断开 `GIT_DIR`、`GIT_WORK_TREE`、`GIT_INDEX_FILE` | F13 | 无兼容代价 |
| revert 先提交、后写回；写回改用原地截断写入而非 rename | F3、F4，$I_4$ | 需要区分「文件不存在」与「符号链接」 |
| revert 目标等于最新版本而磁盘偏离时，拒绝（退出码 4）或记录丢弃版本 | F5 | 行为变更 |
| 纳管时生成盐并存索引，或纳管前检查 ID 冲突 | F8，$I_1$ | 旧条目不可回填 |
| 基线提交先于索引写入；失败时回滚索引 | F6，$I_3$ | `commitVersion` 当前不依赖索引，可换序 |
| `verify` 增加双向检查：空版本条目、重复 ID、孤儿 blob、非 bakon 提交 | F7、F1 | 只读检查，可先只报不改 |
| `max_versions` 用空值区分「未设置」与 `0`，或定义 `-1` 为不限制 | F9 | 索引字段语义变更，需文档同步 |
| `diff` 的差异哨兵与错误路径分离；退出码改由哨兵错误分类 | F10 | 内部重构，无外部代价 |
| 钩子执行前注入 `BAKON_HOOK=1`，需要写锁的子进程立即以 4 退出 | F11 | 依赖子进程配合，覆盖不全 |
| 锁改用带超时的 `LockContext`，超时映射退出码 4 并提示 | 可观测性 | 需要选择默认超时 |
| `gc` 改用带宽限期的 prune，或让读者在对象缺失时重试一次 | 读-裁剪竞争 | 宽限期牺牲即时回收 |
| prune 成本：短期改为「达到上限的 $k$ 倍才裁剪一次」，长期需按文件分 ref 或分仓库 | F12 | 前者改变保留上限的严格性 |

以下三条属于取舍，不属缺陷：保留「锁内执行钩子」则以 F11 的防护为代价换取顺序保证；保留「读不取锁」则以重试为代价换取不被编辑会话阻塞；保留「索引为文件」则以顺序不变量为代价换取零依赖。

## 6. 独立校验

### 6.1 已执行

- 环境：go1.27.0 linux/amd64；被测代码未修改，`go build` 通过。
- 实验：`/tmp/opencode/design-check.sh`、`design-check2.sh`、`design-check3.sh`，以及锁阻塞与仓库重写两段独立脚本；全部在隔离 `BAKON_HOME` 与临时目录下运行，未触碰用户配置与真实仓库。
- 交叉验证方式：同一结论用两种输入形态复现（例如 F1 用「子目录 store」与「根目录 store」分别验证，前者失败于读取、后者失败于历史重建）；F9 先以全局上限触发裁剪，再以 `index.json` 显式写 0 复测，排除配置解析错误的解释。

### 6.2 未覆盖

- 真实崩溃注入（fsync 与 rename 之间的 SIGKILL）：仅由代码顺序推断，未实测。
- 读操作与 `gc --prune=now` 的竞争：仅由代码路径推断，未构造时序。
- Windows 与 Termux 的路径、shell 与元字符语义：未测。
- 规模曲线：仅测 $|\mathcal{G}| = 100$ 与约 $10$ 两个点，线性外推来自每提交 4 次 git 调用的代码路径，属推断而非测量。

### 6.3 结论所依赖的前提

F1 依赖「store 可指向任意既有仓库」这一当前允许的用法；若该用法被显式禁止，F1 降级为配置错误。F8 依赖「被腾空的路径会被再次纳管」，这是 `mv` 的常规后续动作。F12 依赖「保留检查嵌入每次 edit」，若改为独立定时任务，结论只影响 prune 本身的耗时。F11 依赖「钩子允许调用 bakon」，当前文档未禁止。
