# OPS__store-identity-recovery-and-retention

本报告覆盖存储目录的归属判定、故障恢复手册、空间与备份、格式升级与旧数据政策。它解释为什么 0.x 的仓库判定会写坏别人的项目，并给出 v1 的替代规则。

## 1. 归属判定

存储根目录必须包含标记文件 `BAKON_STORE`：

```json
{ "schema": 1, "uuid": "…", "created": "2026-11-10T12:00:00Z", "tool": "bakon/1.0" }
```

打开规则，按顺序判定：

| 目录状态 | 行为 |
|---|---|
| 不存在 | 创建目录与标记，继续 |
| 存在且为空 | 写入标记，继续 |
| 存在、非空、有标记 | 校验 `schema` 后继续 |
| 存在、非空、无标记 | 拒绝，退出 6，提示目标不是 bakon 存储 |
| 有标记、`schema` 高于本程序 | 拒绝，退出 6，提示升级 |
| 有标记、`schema` 低于本程序 | 拒绝，退出 6，提示需要迁移 |

「非空」指除 `.`、`..` 外至少有一个条目。拒绝而不是「尽力而为」，因为写入一个不属于自己的目录是不可逆的副作用。

默认存储位置按优先级：`--store` > `BAKON_STORE` > 配置 `store` > `BAKON_HOME/store` > `~/.bakon/store`。v1 不使用 0.x 的 `~/.bakon/repo`，两者可以并存。

## 2. 为什么 0.x 的判定是错的

0.x 用

```text
git -C <store> rev-parse --is-inside-work-tree
```

判定「仓库是否已存在」。令 $W(d)$ 表示「$d$ 位于某个工作树内」，$R(d)$ 表示「$d$ 本身是仓库根」。该命令回答 $W(d)$，而初始化需要的是 $R(d)$。二者不等价：

$$W(d) \not\Rightarrow R(d)$$

反例即审计中的 F1/F2：$d$ 是 `~/dotfiles/repo` 时 $W(d)$ 为真而 $R(d)$ 为假，Bakon 跳过初始化，把提交写进 `~/dotfiles`；$d$ 恰好是 `~/dotfiles` 本身时 $R(d)$ 为真，但那是别人的仓库，prune 会按「每提交一路径」的前提重放它，多文件提交的其余路径被丢弃。

v1 的判定不再依赖任何外部命令：标记文件给出归属，`schema` 给出兼容性，目录内容给出「是否可能装着他人的数据」。三者都是本地事实，不需要推断。

## 3. 故障恢复手册

| 现象 | 原因 | 处理 |
|---|---|---|
| `index.json` 缺失或损坏 | 缓存丢失 | 无需处理：查找会扫描清单并重建；或执行 `verify --fix` |
| `.pending` 存在 | 上次回退未完成写回 | 任意命令启动时自动补齐；也可显式 `verify --fix` |
| 对象缺失 | 手动删除、介质损坏 | `verify` 报 6 并列出文件与版本；可从备份恢复该对象 |
| 清单 JSON 解析失败 | 半写、外部编辑 | 退出 6 并指出文件；用备份替换该清单 |
| `trash/` 非空 | 裁剪中断 | 启动时清空；无引用对象已不在清单中 |
| 版本存在但目标文件已被外部修改 | 用户绕过程序编辑 | `edit` 会把它记为下一版；`revert` 默认拒绝（退出 4），`--force` 先记 `salvage` |
| `pending` 标记反复出现 | 写回持续失败（只读挂载、权限） | 退出 7；修复权限后重试 |

恢复原则：**清单是事实，对象是内容，目标文件是投影**。三者中任意一个损坏，处理方式都不同，不能互相推断。

## 4. 空间

单个文件的占用约为：

$$\sum_{v \in V} \mathrm{deflate}(\text{content}(v)) + |V| \cdot c + c_{\text{manifest}}$$

其中 $c$ 为对象文件的开销（近似目录项与元数据），$c_{\text{manifest}}$ 为清单的固定开销。保留上限同时约束 $|V|$，因此空间是可控的。

提供 `bakon verify --size` 输出每个文件的对象字节数、去重后总量与清单开销，用于容量判断。不提供自动全局配额：静默删除用户历史不是本工具该做的决定。

## 5. 备份与恢复

- 备份：完整复制存储目录。清单与对象在同一目录树内，任意时刻的副本都是自洽的（崩溃点定理保证）。
- 恢复：复制回同一路径或新路径，用 `--store` 指向；执行 `verify`。
- 迁移到新机器：同一路径规则；路径变化后，旧清单里的 `path` 与实际不符，需要 `bakon mv` 或 `verify --fix` 的路径修复模式。

不做增量备份、不做云端同步：单机工具，把边界留给系统工具（rsync、快照）。

## 6. 格式升级

- `schema` 出现在标记与每个清单中。
- 读取时要求 `schema` 等于本程序支持的值；低于则提示迁移命令（v1.0 无迁移，直接拒绝），高于则提示升级程序。
- 不实现「向后兼容的宽松解析」：猜错字段比拒绝服务更危险。
- 升级路径由程序内置，一次只升一个版本，升级前自动备份目录（`store.bak.<schema>`）。

## 7. 旧数据政策

v1.0 不读取 0.x 的 `repo/`，也不删改它。理由：

- 旧存储在 git 对象库里，读取它需要 git 或自行实现对象格式与 delta 解码，二者都与「去掉 git 依赖」冲突。
- 保留旧目录与旧二进制，用户可自行导出需要的版本后再切换。
- 迁移工具作为后续特性：编译期 feature `legacy-git`，显式构建时才引入 git 调用，默认产物保持零依赖。

文档必须写明这一点，避免用户在升级后发现历史「不见了」——历史没有消失，只是在另一个目录里。

## 8. 运行手册摘要

| 目标 | 命令 |
|---|---|
| 初始化存储 | `bakon init`（或首次 `edit` 自动初始化空目录） |
| 健康检查 | `bakon verify`，必要时 `--fix` |
| 查看占用 | `bakon verify --size` |
| 手动裁剪 | `bakon prune [<file>]` |
| 查看存储位置 | `bakon config show` |
| 迁移机器 | 复制目录，`bakon verify` |
| 出问题 | 按第 3 节表格定位，先备份目录再操作 |

## 9. 最弱前提

- 标记文件不被外部删除或替换。若被删除，程序会把目录视为「非 bakon 存储」并拒绝写入——这是有意的保守行为。
- 文件系统支持 `fsync` 目录；在不支持该语义的平台上，崩溃恢复退化为「可能丢失最后一次提交」，不产生混合状态。
